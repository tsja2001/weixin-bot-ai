# 重构后架构说明

这次重构之后，项目从“一个 bot.js 里包办大部分事情”，调整成了“微信机器人 + 文档解析服务 + OCR 服务”三个主要部分。整体目的不是把项目做复杂，而是把不同职责拆开，后面继续加功能时更容易维护。

## 1. 现在的整体结构

```text
微信用户
  -> weixin-bot
  -> document-service
  -> ocr-service
```

简单理解：

```text
weixin-bot          负责微信连接、收消息、发消息、调用 AI
document-service    负责解析 PDF、Word、Excel、PPT、TXT 等文件
ocr-service         负责图片 OCR，把图片里的文字识别出来
```

也就是说，微信机器人现在不再自己解析复杂文件，而是把文件交给 `document-service`。如果遇到扫描版 PDF，`document-service` 再去调用 `ocr-service`。

## 2. 每个部分负责什么

### weixin-bot

这是微信机器人主程序，仍然是每个微信实例各跑一个。

它主要负责：

```text
1. 连接微信 iLink
2. 接收用户消息
3. 下载并解密微信发来的文件或图片
4. 把文件交给 document-service 解析
5. 把解析后的内容暂存起来，等待用户下一句要求
6. 调用 AI 接口生成回复
7. 发送回复到微信
8. 自动重连、定时任务、每日统计
```

它不再负责：

```text
1. PDF 渲染
2. PDF 文本层提取
3. Office 文档解析
4. 调用 OCR 处理 PDF 页面
```

这些都迁移到了 `document-service`。

### document-service

这是这次新增的服务，端口是：

```text
http://127.0.0.1:8770
```

它主要负责：

```text
1. 解析 PDF
2. 解析 DOCX
3. 解析 TXT
4. 解析 Excel
5. 解析 PPTX
6. 判断 PDF 是否应该走文本层，还是需要 OCR
7. 把短 PDF 转成图片，交给 AI vision
8. 对扫描版 PDF 调用 ocr-service
```

以后如果文件解析能力继续增强，比如增加更多格式、做解析缓存、优化混合 PDF 策略，优先都放在这个服务里。

### ocr-service

这是原来已经有的 Python OCR 服务，端口是：

```text
http://127.0.0.1:8765
```

它只做一件事：

```text
图片进来，识别出文字返回。
```

它不关心微信，也不关心 PDF。PDF 由 `document-service` 渲染成图片后，再交给它识别。

## 3. 用户发文件后的流程

现在用户发文件后，大致流程是：

```text
用户发文件
  -> bot 下载并解密文件
  -> bot 调用 document-service /parse
  -> document-service 判断文件类型
  -> 如果是普通文档，直接提取文字
  -> 如果是 PDF，先看有没有文本层
  -> 如果 PDF 是扫描件，渲染成图片并调用 ocr-service
  -> bot 收到解析结果后暂存
  -> 用户再发“总结一下”“提取重点”等要求
  -> bot 把文件内容和用户要求一起发给 AI
  -> AI 回复
```

这个“两步式”的交互逻辑没有变：用户先发文件，bot 先准备好内容；用户再说要做什么，bot 再结合文件内容处理。

## 4. 当前服务列表

PM2 里现在主要有这些进程：

```text
weixin-bot-1        微信机器人实例 1
weixin-bot-2        微信机器人实例 2
weixin-bot-test     测试微信机器人实例
document-service    文档解析服务
ocr-service         OCR 识别服务
```

查看状态：

```bash
pm2 status
```

查看文档解析服务是否正常：

```bash
curl http://127.0.0.1:8770/health
```

查看 OCR 服务是否正常：

```bash
curl http://127.0.0.1:8765/health
```

## 5. 这次重构带来的变化

最明显的变化是：

```text
bot.js 变轻了
文件解析有独立服务了
OCR 仍然保持独立服务
后续优化文件解析时，不需要频繁改微信主流程
```

好处：

```text
1. 微信连接和文件解析互相解耦
2. PDF/OCR 的优化可以集中在 document-service
3. 后续增加文件格式更清晰
4. 出问题时更容易判断是微信问题、文档解析问题，还是 OCR 问题
5. benchmark 和测试台以后可以逐步复用 document-service 的解析逻辑
```

代价：

```text
1. 多了一个 document-service 进程
2. PM2 里需要同时保证 bot、document-service、ocr-service 都在线
3. 文件解析链路比以前多了一次本机 HTTP 调用
```

这个代价是可以接受的，因为文档解析本来就越来越重，拆出来之后更容易继续扩展。

## 6. 后续建议

后续可以继续做几件事：

```text
1. 把 ocr-demo 也改成调用 document-service，避免测试台和生产逻辑不一致
2. 给 document-service 增加更完整的测试样本
3. 单独优化混合 PDF：第一页扫描、后面有文本层的情况
4. 给 document-service 增加解析结果缓存，避免同一个文件重复 OCR
5. 后面如果实例更多，可以再考虑把会话状态、文件暂存状态持久化
```

现阶段的状态可以理解为：项目已经从“单体 bot 脚本”变成了“微信机器人主流程 + 文档解析服务 + OCR 服务”的小型服务化架构。
