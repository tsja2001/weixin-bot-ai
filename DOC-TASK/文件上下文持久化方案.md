# 文件上下文持久化方案

## 问题分析

当前文件处理存在两个缺陷，结合 `instances/wife/logs/bot.log` 中的真实场景说明：

### 问题 1：多文件覆盖

```
14:36:53  用户上传 会议纪要 模板.pdf  → pendingFiles 存 PDF
14:37:43  用户上传 原文...docx        → pendingFiles 被 docx 覆盖，PDF 丢失
14:37:59  用户说 "把内部会议的内容整成会议纪要模板形式" → 只收到 docx，没有 PDF 模板
14:45:36  用户重新上传 PDF           → 此时 AI 已丢失 docx 内容，只能就 PDF 回复
```

**根因**：`pendingFiles` 是 `Map<fromId, {fileName, text, timestamp}>`，单值结构。第二个文件到达时第一个被直接覆盖。

### 问题 2：文件内容仅一轮有效

当前流程：文件 + 用户指令合并为一条 user message 发给 AI → AI 回复 → 合并消息不入历史。第二轮对话时历史里只有截断后的 2000 字 AI 回复，没有文件原文。

```
第一轮: 用户: [文件8000字] + "根据这个模板改写"  → AI: 回复（记入历史，截断到2000字）
第二轮: 用户: "上一段改一下语气"                 → AI: 看不到文件原文，只能凭第一轮回复猜测
```

**根因**：文件内容从未写入 `conversationHistory`，`sendAiReply` → `addToHistory` 只记录 user 指令 + assistant 回复。

## 方案评估

### 用户提出的方案：文件注入历史记录

> 上传文件后，把解析出的内容作为历史消息钉在上下文里，后续几轮对话一直携带。

**评价：方案正确，这是最直接有效的解法。** 下面对比几种候选路径：

### 候选方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **A. 文件注入历史**（用户方案） | 文件内容作为 user 消息插入 conversationHistory，保留 N 轮 | 自然融入现有滑动窗口；多文件简单拼接；无需改 AI 调用层 | 占历史窗口配额；长文件会挤掉近期对话 |
| B. 文件注入 system prompt | 动态拼接 system prompt，追加文件内容 | 不占 message 配额；文件始终可见 | system prompt 不宜过长（模型对此位置注意力偏弱）；多文件拼接后臃肿；prompt 格式不统一 |
| C. 文件摘要缓存 | 先让 AI 总结文件要点，只存摘要 | 极省 token | 信息损失不可控；增加一次 API 调用；摘要质量决定后续上限 |
| D. Redis / 外部向量存储 | 文件内容写入向量库，对话时检索相关片段 | 理论上支持超大文件 | 引入重型依赖；检索不一定命中；过度工程 |

**结论：选方案 A。** 对于微信场景（单次对话通常在 20 轮以内，文件数量 1-5 个），方案 A 最务实，不需要新依赖，改动集中在 `bot.js` 内。

## 详细设计

### 核心概念：文件锚点（File Anchor）

文件上传后不只是一次性地拼进用户消息，而是作为"文件锚点消息"插入对话历史，在后续 N 轮中持续携带。

```
普通历史:  [用户] [AI] [用户] [AI] [用户] [AI] ...
加上锚点:  [文件A] [文件B] [用户] [AI] [用户] [AI] [用户] [AI] ...
            ↑ 这两条在开头固定，每轮都一起发给 AI
```

### 数据结构变更

```js
// 旧：单文件 Map
const pendingFiles = new Map();
// fromId → {fileName, text, timestamp}

// 新：多文件数组 Map
const pendingFiles = new Map();
// fromId → {
//   files: [{fileName, text, type, images, timestamp}],
//   timestamp: <最早文件的时间戳>
// }

// 新增：文件锚点 Map（与 conversationHistory 独立管理）
const fileAnchors = new Map();
// fromId → [
//   {role: "user", content: "[用户上传了文件: xxx.docx]\n\n<文件内容>", turnCount: 0}
// ]
```

### 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `FILE_ANCHOR_MAX_CHARS` | **50000** | 单个文件锚点的硬上限（约 90K tokens）。覆盖极端长的 OCR 文档 |
| `FILE_ANCHOR_TOTAL_CHARS` | **50000** | **所有文件锚点总和上限**。单文件可以独占全部配额；多文件共享，超出时按比例截断 |
| `FILE_ANCHOR_MAX_TURNS` | **10** | 文件锚点保留的对话轮数（与 60 分钟 TTL 协同：无论哪个先到，文件都会清除） |
| `FILE_ANCHOR_MAX_FILES` | **5** | 同时锚定的文件数量上限（实际由 TOTAL_CHARS 约束主导） |
| `PENDING_FILE_TTL_MS` | **12h** | 待处理文件过期时间。允许上午上传文件、下午再发指令 |

### 两级截断机制

```
单文件内容
  → 超过 FILE_ANCHOR_MAX_CHARS (50K)？ → 截断到 50K
  → 全部文件总和超过 FILE_ANCHOR_TOTAL_CHARS (50K)？ → 按比例压缩每个文件
  → 都不超 → 全量保留
```

实际效果：

| 场景 | 结果 |
|------|------|
| 1 个 5 万字 OCR 文档 | 全量保留 |
| 3 个文档各 1.5 万字 | 全量保留（总计 4.5 万） |
| 5 个文档各 3000 字 | 全量保留（总计仅 1.5 万） |
| 2 个文档各 4 万字 | 总量触顶 5 万，按比例截断到各 2.5 万 |

### 参数规模参照

| 量级 | Token 数 | 中文字数 | 参照物 |
|------|---------|---------|--------|
| 单文件上限 | ~90K | 50000 | 约 50-60 页 A4 中文 |
| 全部文件总和上限 | ~90K | 50000 | 一份完整制度手册；或 5 份常规文档 |
| 10 轮普通历史 | ~72K | ~40000 | 10 轮满额对话 |
| system + output | ~5K | — | 系统提示 + 4096 output |
| **合计上限** | **~167K** | — | 200K 窗口下仍有 33K 余量 |

> **注意**：首次文件+指令的合并消息中，文件仍用**原文全文**（不截断），确保 AI 第一轮有完整信息。截断仅针对后续轮次的锚点版本。

### 处理流程（变更后）

```
1. 用户上传文件 A
   → pendingFiles[fromId].files.push({fileName, text: fileAText, timestamp})

2. 用户上传文件 B（在步骤 3 之前）
   → pendingFiles[fromId].files.push({fileName, text: fileBText, timestamp})

3. 用户发送文本 "请对比这两份文件"
   → 检查 pendingFiles[fromId]，有 [文件A, 文件B]
   → 构建合并消息:
      [用户之前发送了以下 2 个文件]
      
      === 文件1: 会议纪要模板.pdf ===
      <fileAText>
      
      === 文件2: 内部会议.docx ===
      <fileBText>
      
      [用户要求]
      请对比这两份文件
   → 调用 AI 获得回复
   → 写入历史:
      - 文件锚点 A: "[用户上传了文件: 会议纪要模板.pdf]\n\n<fileAText，按 TOTAL_CHARS 预算截断>"
      - 文件锚点 B: "[用户上传了文件: 内部会议.docx]\n\n<fileBText，按 TOTAL_CHARS 预算截断>"
      - 用户消息: "请对比这两份文件"
      - AI 回复
   → 清除 pendingFiles[fromId]

4. 用户继续对话 "把第二份改成第一份的格式"
   → getHistoryForUser 返回: [锚点A, 锚点B, 历史消息...]
   → AI 能看到两份文件内容 + 全部对话历史
   → fileAnchors[fromId] 中每条 turnCount += 1

5. 对话进行到第 11 轮
   → 锚点 turnCount 达到 10，自动移除
   → 后续对话不再携带文件内容
```

### 关键函数变更

**`getHistoryForUser(fromId)`** 改为拼接文件锚点：

```js
function getHistoryForUser(fromId) {
  const entry = conversationHistory.get(fromId);
  const anchors = fileAnchors.get(fromId) || [];

  // 过滤过期锚点（轮数超限或 TTL 超时）
  const activeAnchors = anchors.filter(a => a.turnCount < FILE_ANCHOR_MAX_TURNS);
  if (activeAnchors.length !== anchors.length) {
    fileAnchors.set(fromId, activeAnchors);
  }

  if (!entry && activeAnchors.length === 0) return [];
  if (entry && Date.now() - entry.lastActivity > HISTORY_TTL_MS) {
    conversationHistory.delete(fromId);
    fileAnchors.delete(fromId);
    return [];
  }

  if (entry) entry.lastActivity = Date.now();
  // 锚点在前，对话历史在后
  return [...activeAnchors, ...(entry?.messages || [])];
}
```

**`buildFileAnchors(files)`** 两级截断逻辑：

```js
function buildFileAnchors(files) {
  // 第一级：单文件不超过 MAX_CHARS
  const step1 = files.map(f => ({
    ...f,
    text: f.text.length > FILE_ANCHOR_MAX_CHARS
      ? f.text.slice(0, FILE_ANCHOR_MAX_CHARS)
      : f.text,
  }));

  // 第二级：总和不超过 TOTAL_CHARS
  const totalChars = step1.reduce((sum, f) => sum + f.text.length, 0);
  if (totalChars <= FILE_ANCHOR_TOTAL_CHARS) return step1;

  // 按比例压缩
  const ratio = FILE_ANCHOR_TOTAL_CHARS / totalChars;
  return step1.map(f => ({
    ...f,
    text: f.text.slice(0, Math.floor(f.text.length * ratio)),
  }));
}
```

**`sendAiReply` 中增加锚点写入**：文件合并消息发送后，将截断版文件内容写入 `fileAnchors`，并递增已有锚点的 `turnCount`。

**`pendingFiles` 处理**：
- `set` 改为追加：检查已有条目，合并 files 数组
- `delete` 在处理完所有文件后统一执行

### 额外功能：清除文件上下文

新增 `/清空文件` 指令，手动移除当前对话的文件锚点：

```
用户: /清空文件
Bot:  已清除当前对话中的 2 个文件上下文。
```

实现：
```js
if (cmd === "/清空文件") {
  fileAnchors.delete(fromId);
  await sendMsgSafe(fromId, contextToken, "已清除文件上下文。");
  continue;
}
```

同步更新 `/help` 输出和 `COMMANDS_MSG`。

### 不影响的行为

- 图片消息（type=2）不受影响，仍走原有 pending + 合并流程
- 对话记忆 60 分钟 TTL 不受影响（文件锚点一同清除）。注意：文件锚点可能比对话历史活得更久——如果用户在 60 分钟内持续对话，锚点可存活 10 轮；一旦停止对话 60 分钟，两者一起清空
- `pendingFiles` TTL 延长到 12 小时，允许跨上下午
- 历史截断 `HISTORY_MAX_CONTENT_LEN = 2000` 仅对普通消息生效，文件锚点使用独立的两级截断机制
- `/help` `/time` `/重新连接` 等指令行为不变

## Token 预算详细计算

以 Claude Opus 4.7（200K context window）为基准，1 中文字 ≈ 1.8 tokens。

### 典型场景

| 组件 | 字符数 | Token 估算 | 占比 |
|------|--------|-----------|------|
| System prompt | ~1000 | ~2000 | 1% |
| 文件锚点（2-3 个文档，总计 2 万字） | 20000 | ~36000 | 18% |
| 对话历史 10 轮 | ~40000 | ~72000 | 36% |
| 当前消息 + output | ~5000 | ~9000 | 4.5% |
| **合计** | ~66000 | **~119K** | **60%** |

### 极限场景

| 组件 | 字符数 | Token 估算 | 占比 |
|------|--------|-----------|------|
| System prompt | ~2000 | ~4000 | 2% |
| 文件锚点总和（触顶） | 50000 | ~90000 | 45% |
| 对话历史 10 轮（满 2000/条） | ~40000 | ~72000 | 36% |
| 当前消息 + output | ~5000 | ~9000 | 4.5% |
| **合计** | ~97000 | **~175K** | **87%** |

**即使在极限场景下仍有约 25K tokens（13%）的安全余量。** 实际使用极少触及此极限：

1. `FILE_ANCHOR_TOTAL_CHARS = 50000` 硬顶确保不会超
2. 大多数文档解析结果远小于 5 万字（从 wife 日志看，常规文档 1000-10000 字）
3. 对话历史不会每条都恰好卡在 2000 字截断线
4. 10 轮或 60 分钟 TTL 先到者生效，自然淘汰旧内容

## 风险与边界

1. **文件锚点截断可能导致信息丢失**：两级截断中，单个文件超 5 万字或总和超 5 万字时保留前 N 字。对公文/制度/合同类文档，关键信息通常在前半部分，头截断损失可控。如果遇到附录型文档（关键信息在末尾），可后续调整为"头+尾"策略（如前 3 万 + 后 2 万）。

2. **锚点总量 vs 历史轮数的博弈**：5 万字文件锚点 + 10 轮满额历史 ≈ 175K tokens。如果用户反馈"对话记忆变短了"，可将 `FILE_ANCHOR_TOTAL_CHARS` 降至 35000 或 `HISTORY_MAX_TURNS` 降至 8。

3. **图片 + 文件混合场景**：当前图片走独立 pending 路径（type=image），与文件锚点方案互不冲突。图片仅在第一轮作为 content block 发送，不入文件锚点历史（图片 base64 太长，不适合多轮携带）。

4. **PDF OCR 文本极长的情况**：OCR 可能产出超过 5 万字。首次合并消息用全文（以确保第一轮完整呈现），锚点版受 5 万字硬顶截断。这是有意的折衷。

5. **12 小时 TTL 与 60 分钟历史 TTL 的交互**：pendingFiles 可以等 12 小时，但 conversationHistory 在 60 分钟无活动后自动清空。这意味着如果用户上传文件后 2 小时才发指令，文件还在 pending，但之前的对话历史已经清空——这正好是合理的：旧话题自然遗忘，新话题从文件+指令开始。

6. **`/清空文件` 后历史中不再携带文件**，但对话记忆本身不受影响——清空的是文件上下文，不是整个对话。
