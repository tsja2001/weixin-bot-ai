# 飞书自动汇总测试方案

## 测试目标

确保飞书自动汇总功能稳定、可控、可用。

重点验证：

- TSJA 实例聊天记录可以稳定写入飞书多维表格。
- 多维表格字段顺序符合人工查看要求。
- 每轮记录准确对应一条用户消息和一条 AI 回复。
- 附件解析内容可以进入对应字段。
- token 统计按单轮准确写入。
- 每日 20:00 简报可以生成。
- 飞书异常不会影响微信机器人正常回复。
- 后续复制到 wife 后，多实例、多飞书账号不会互相污染。

## 测试范围

包含：

- 配置校验。
- 字段格式化。
- 摘要生成。
- token 记录。
- 附件内容收集。
- 本地队列。
- lark-cli 调用封装。
- 飞书多维表格写入。
- 每日简报生成。
- TSJA 和 wife 多实例隔离。

不包含：

- 飞书开放平台自身可用性测试。
- iLink 平台稳定性测试。
- 大模型输出质量的主观长期评估。

## 测试环境

### 本地测试环境

使用项目已有本地 HTTP 测试通道：

```bash
node tests/runner.js
```

本地测试用于验证机器人主流程不被破坏。

### TSJA 真实联调环境

实例：

```text
instances/tsja
```

飞书：

- 使用当前已授权 profile。
- 使用 TSJA 专用测试多维表格。
- 测试阶段建议先建独立测试表，避免污染正式数据。

### wife 验证环境

实例：

```text
instances/wife
```

飞书：

- wife 独立 profile。
- wife 独立多维表格。

wife 只在 TSJA 验证通过后测试。

## 测试数据准备

### 多维表格字段

测试表必须包含以下字段，并保持顺序：

1. 摘要
2. 时间
3. 用户内容
4. AI回复内容
5. 附件内容
6. 附件名称
7. 输入Token
8. 输出Token
9. 总Token
10. 日期
11. 实例
12. 微信用户ID
13. 记录ID
14. 主模型
15. 摘要模型
16. 同步状态
17. 错误信息

验收时必须在飞书界面确认前四列顺序。

### 测试文件

准备以下文件：

- 短文本 `.txt`，内容 100 字以内。
- 长文本 `.txt`，内容超过 20000 字。
- 普通 `.docx`。
- 可解析 PDF。
- 扫描 PDF 或图片类 PDF，如果 OCR 服务可用。

### 测试消息

准备以下用户输入：

```text
你好，帮我写一段今日工作总结。
```

```text
根据刚才的文件，提炼 3 个重点。
```

```text
继续基于这个文件，给我列待办事项。
```

```text
/help
```

```text
/time
```

## 单元测试

### 配置校验

用例：

1. `feishu_summary.enabled` 为 false。
2. 缺少 `feishu_summary`。
3. 缺少 `profile`。
4. 缺少 `base_app_token`。
5. 缺少 `table_id`。
6. 配置完整。

预期：

- 配置缺失时不抛出致命异常。
- 功能自动禁用并输出明确日志。
- 配置完整时返回标准化配置。

### 字段格式化

用例：

1. 普通文本对话。
2. 带附件对话。
3. 多附件对话。
4. 用户内容为空或异常。
5. AI 回复很长。
6. 附件内容超过长度限制。

预期：

- 字段名正确。
- 前四字段逻辑顺序为：摘要、时间、用户内容、AI回复内容。
- `总Token = 输入Token + 输出Token`。
- 附件内容超长时被截断并带提示。
- `记录ID` 稳定且非空。

### 摘要生成

用例：

1. Deepseek 正常返回 20 字以内摘要。
2. Deepseek 返回超过 20 字。
3. Deepseek 返回带引号或 `摘要：` 前缀。
4. Deepseek 请求失败。
5. 用户内容极短。

预期：

- 最终摘要不超过 20 字。
- 去掉无意义前缀和包裹引号。
- 失败时使用本地兜底摘要。
- 摘要为空时使用 `未命名对话` 或用户内容截断。

### token 记录

用例：

1. AI 接口返回 `input_tokens`、`output_tokens`。
2. AI 接口返回 `prompt_tokens`、`completion_tokens`。
3. AI 接口不返回 usage。
4. AI 接口失败。

预期：

- 正常映射 input/output token。
- 不返回 usage 时 token 记为 0。
- 失败兜底也能写入结构化结果。
- `dailyStats` 和单条记录 usage 不互相冲突。

### lark-cli 封装

用例：

1. 正常写入返回成功。
2. exit code 非 0。
3. stdout 不是 JSON。
4. 飞书限流。
5. 网络失败。
6. profile 缺失。

预期：

- 不使用 shell 拼接命令。
- 所有调用显式传入 `--profile`。
- 错误被分类为可重试或不可重试。
- stdout/stderr 被记录到日志。

### 队列

用例：

1. 写入一条 pending 记录。
2. 同步成功后标记 synced。
3. 同步失败后保留 failed。
4. 进程重启后重试 failed。
5. 重复处理同一个记录ID。

预期：

- 本地 JSONL 可追溯。
- 重复记录不会造成多维表格重复写入，或至少可以通过记录ID识别重复。
- 队列损坏单行不影响后续行处理。

## 本地集成测试

使用已有 local-channel 测试框架增加场景。

### 普通聊天

步骤：

1. 启动本地测试实例。
2. 发送普通文本消息。
3. 等待机器人回复。
4. 检查本地飞书 mock 是否收到一条写入请求。

预期：

- 微信回复正常。
- 飞书写入事件包含用户内容和 AI回复内容。
- 字段顺序符合要求。

### 指令不入库

步骤：

1. 发送 `/help`。
2. 发送 `/time`。

预期：

- 机器人正常返回指令响应。
- 不生成聊天记录入库事件。

### 文件对话

步骤：

1. 发送测试文件。
2. 等待解析完成提示。
3. 发送“根据刚才的文件总结重点”。
4. 等待 AI 回复。
5. 检查飞书写入事件。

预期：

- 用户内容为用户的总结指令。
- 附件名称非空。
- 附件内容包含解析文本。
- AI回复内容非空。

### 历史附件追问

步骤：

1. 发送文件。
2. 发送第一次文件相关问题。
3. 发送第二次“继续基于这个文件列待办事项”。
4. 检查第二条记录。

预期：

- 第二条记录仍包含附件内容或附件引用。
- AI 回复和用户追问对应同一轮。

### 飞书失败不影响回复

步骤：

1. 将飞书 mock 设置为失败。
2. 发送普通消息。
3. 等待机器人回复。

预期：

- 微信回复正常。
- 本地队列记录 failed。
- 日志包含失败原因。

### 飞书慢响应不阻塞

步骤：

1. 将飞书 mock 延迟 10 秒返回。
2. 发送普通消息。
3. 记录用户收到 AI 回复的时间。

预期：

- AI 回复不等待飞书完成。
- 飞书最终成功或进入队列重试。

## TSJA 真实飞书冒烟测试

### 授权状态检查

命令：

```bash
lark-cli --profile cli_aaa83f5fcf229bfc auth status
```

预期：

- user identity ready。
- tokenStatus valid。
- scopes 包含 `base`、`docs`、`drive`。

### 多维表格写入检查

步骤：

1. 给 TSJA 机器人发送普通文本。
2. 等待 AI 回复。
3. 打开飞书多维表格。

预期：

- 新增一条记录。
- 前四列依次为：摘要、时间、用户内容、AI回复内容。
- 摘要不超过 20 字。
- 时间为当前 Asia/Shanghai 时间。
- 实例字段为 `tsja`。
- 同步状态为 `synced`。

### 附件写入检查

步骤：

1. 给 TSJA 发送一个 `.txt` 或 `.docx`。
2. 发送“总结这个文件”。
3. 打开多维表格检查记录。

预期：

- 附件名称正确。
- 附件内容包含解析文字。
- 用户内容是“总结这个文件”。
- AI回复内容是本轮回复。

### token 检查

步骤：

1. 发送普通消息。
2. 查看多维表格 token 字段。
3. 查看日志中 AI usage。

预期：

- 输入Token和输出Token为数字。
- 总Token等于两者之和。
- 与日志中 usage 基本一致。

### 20:00 日报检查

步骤：

1. 在测试环境可临时把任务时间改为当前时间后 2 分钟。
2. 触发 `feishu_daily_summary`。
3. 检查日报写入目标。

预期：

- 日报包含当天对话数量。
- 日报包含主要话题和重要结论。
- 日报包含 token 汇总。
- 无对话时输出“今日无聊天记录”或类似明确内容。

## 多实例隔离测试

在 TSJA 稳定后执行。

### wife profile 检查

步骤：

1. 配置 wife 独立 profile。
2. 执行：

```bash
lark-cli --profile <wife_profile> auth status
```

预期：

- 显示 wife 对应飞书账号。
- token 有效。

### TSJA 和 wife 写入隔离

步骤：

1. TSJA 发送一条消息。
2. wife 发送一条消息。
3. 分别打开两个多维表格。

预期：

- TSJA 数据只进入 TSJA 表。
- wife 数据只进入 wife 表。
- 两边记录的实例字段正确。
- 不出现 profile 混用。

### 配置缺失隔离

步骤：

1. 临时关闭 wife 的 `feishu_summary.enabled`。
2. wife 发送消息。
3. TSJA 发送消息。

预期：

- wife 不写入飞书，但微信回复正常。
- TSJA 仍正常写入。

## 异常测试

### 飞书 profile 失效

步骤：

1. 使用不存在的 profile。
2. 发送 TSJA 消息。

预期：

- 微信正常回复。
- 飞书记录进入 failed。
- 错误信息明确提示 profile 问题。

### 多维表格字段缺失

步骤：

1. 删除或重命名测试表中的一个字段。
2. 发送消息。

预期：

- 写入失败或字段校验失败。
- 错误被记录。
- 微信回复不受影响。

### 飞书限流

步骤：

1. 快速发送多条消息，或 mock 返回限流错误。

预期：

- 可重试错误进入队列。
- 不造成进程崩溃。
- 日志中有重试提示。

### 大附件

步骤：

1. 上传超过 20000 字解析文本的文件。
2. 发送总结请求。

预期：

- 多维表格附件内容被截断。
- 截断提示存在。
- AI 正常回复。

### AI 摘要失败

步骤：

1. 将摘要模型配置为不可用模型。
2. 发送消息。

预期：

- 主 AI 回复正常。
- 摘要使用本地兜底。
- 记录仍写入。

## 回归测试

每次修改后必须执行：

```bash
node tests/runner.js
```

需要重点确认：

- 普通聊天仍正常。
- 文件解析仍正常。
- 图片暂存仍正常。
- `/help`、`/time`、`/重新连接` 等指令仍正常。
- `daily_report` 原有行为未被破坏。
- 本地测试通道未被破坏。

## 上线步骤

1. 在 TSJA 测试表完成字段创建。
2. 配置 TSJA `feishu_summary.enabled = true`。
3. PM2 重启 TSJA。
4. 执行普通文本冒烟测试。
5. 执行附件冒烟测试。
6. 临时调整日报时间，执行日报冒烟测试。
7. 恢复日报时间为 20:00。
8. 观察 1 天日志和飞书记录。
9. TSJA 稳定后配置 wife profile 和表格。
10. 执行 wife 隔离测试。

## 回滚方案

如果上线后出现异常：

1. 将对应实例 `config.json` 中设置：

```json
{
  "feishu_summary": {
    "enabled": false
  }
}
```

2. 重启对应 PM2 实例。

3. 保留 `logs/feishu_summary_queue.jsonl` 供后续排查。

回滚要求：

- 关闭飞书汇总后，微信机器人必须继续正常工作。
- 不删除已有队列和日志。
- 不影响其他实例。
