# 本地 HTTP 测试通道 — 使用指南

## 这是什么

在微信 bot 的开发过程中，每次功能改动都需要：手动重启服务 → 微信扫码登录 → 真人发消息/上传文件 → 肉眼观察结果。这条链路慢、不可重复、无法自动化。

本地 HTTP 测试通道在 bot 内部嵌入了一个轻量 HTTP 服务器，让你可以通过 curl 命令发送消息给 bot、拉取 bot 的回复、查看内部状态。**原来的微信通道丝毫不受影响**——只在设置了 `LOCAL_TEST_PORT` 环境变量时才会激活。

## 一分钟快速体验

```bash
# 1. 进入测试实例目录
cd /opt/weixin-bot-ai/instances/test-local

# 2. 启动测试 bot（端口 19527）
LOCAL_TEST_PORT=19527 node ../../bot.js

# 在另一个终端：

# 3. 发一条消息
curl -s -X POST http://127.0.0.1:19527/local/inbox/text \
  -H "Content-Type: application/json" \
  -d '{"text":"你好，做个自我介绍"}'

# 4. 拉取 bot 的回复（等最多 15 秒）
curl -s "http://127.0.0.1:19527/local/outbox?since=0&wait_ms=15000" | python3 -m json.tool
```

你会看到类似这样的输出：

```json
{
  "events": [
    {"seq": 1, "kind": "typing", "to_user_id": "local:default", "status": 1},
    {"seq": 2, "kind": "message", "to_user_id": "local:default", "text": "你好！我是AI助手..."},
    {"seq": 3, "kind": "typing", "to_user_id": "local:default", "status": 2}
  ],
  "next_seq": 4
}
```

## 架构（一句话）

bot 原来的消息处理逻辑完全不变。只是在入口处多了一条路——本地 HTTP 注入的消息会和微信消息合并在一起进入同一段处理流程；在出口处，发给 `local:` 开头的用户的消息会进入 HTTP outbox，发给真实用户的消息照常走微信 API。

## API 速查

所有接口返回 JSON，绑定 `127.0.0.1`。

### 发送消息

```bash
# 文本消息
curl -X POST :9527/local/inbox/text \
  -H "Content-Type: application/json" \
  -d '{"text": "你好"}'

# 文件消息（自动解析 docx/pdf/txt/xlsx/pptx）
curl -X POST :9527/local/inbox/file \
  -H "Content-Type: application/json" \
  -d '{"file_path": "/path/to/doc.docx"}'

# 图片消息
curl -X POST :9527/local/inbox/image \
  -H "Content-Type: application/json" \
  -d '{"file_path": "/path/to/photo.jpg"}'

# 多用户隔离：指定不同的 user_id
curl -X POST :9527/local/inbox/text \
  -H "Content-Type: application/json" \
  -d '{"user_id": "local:user_a", "text": "我是用户A"}'
```

### 接收回复

```bash
# 增量拉取（推荐：用 since + next_seq 避免漏事件）
curl -s ":9527/local/outbox?since=0&wait_ms=15000"

# 返回 { events: [...], next_seq: 3 }
# 下次用 since=3 继续拉
curl -s ":9527/local/outbox?since=3&wait_ms=15000"
```

outbox 事件类型：

| kind | 说明 |
|------|------|
| `message` | bot 发送的文本回复 |
| `typing` | "正在输入"状态（status=1 开始，status=2 结束） |

### 查看内部状态

```bash
# 查看某个用户的完整状态
curl -s ":9527/local/state?user_id=local:default" | python3 -m json.tool
```

返回内容包括：
- `pending_files` — 用户上传了但还没发指令的文件列表
- `file_anchors` — 已写入对话记忆的文件锚点
- `conversation_history` — 对话历史（消息条数、最后活跃时间）
- `daily_stats` — 当日消息数和 token 消耗

### 清理与重置

```bash
# 清理某个用户的所有状态（对话、文件、outbox）
curl -X POST :9527/local/reset \
  -H "Content-Type: application/json" \
  -d '{"user_id": "local:default"}'
```

### 健康检查

```bash
curl :9527/local/health
# {"ok":true,"instance_dir":"/opt/weixin-bot-ai/instances/test-local"}
```

## 常见测试场景

### 场景 1：纯文本多轮对话

```bash
# 第一轮
curl -X POST :9527/local/inbox/text -d '{"text":"我叫小明"}'
sleep 5

# 第二轮 —— bot 应该记住"小明"
curl -X POST :9527/local/inbox/text -d '{"text":"我叫什么名字？"}'

# 拉取第二轮回复
curl -s ":9527/local/outbox?since=2&wait_ms=15000" | python3 -m json.tool
# 断言: events 中的 text 应包含"小明"
```

### 场景 2：上传文件后提问

```bash
# 1. 发文件
curl -X POST :9527/local/inbox/file \
  -d '{"file_path":"/opt/weixin-bot-ai/instances/test-local/fixtures/sample.docx"}'

# 2. 拉取解析确认（应收到"已收到...解析出约 X 字内容"）
curl -s ":9527/local/outbox?since=0&wait_ms=10000"

# 3. 发指令（bot 会把文件内容和指令一起发给 AI）
curl -X POST :9527/local/inbox/text -d '{"text":"总结这份文件"}'

# 4. 拉取 AI 回复
curl -s ":9527/local/outbox?since=2&wait_ms=30000" | python3 -m json.tool
```

### 场景 3：指令测试

```bash
# /help
curl -X POST :9527/local/inbox/text -d '{"text":"/help"}'
# 期望：回复包含"可用指令"列表

# /time
curl -X POST :9527/local/inbox/text -d '{"text":"/time"}'
# 期望：回复包含"当前连接剩余时间"

# /清空文件
curl -X POST :9527/local/inbox/text -d '{"text":"/清空文件"}'
# 期望：回复包含"当前没有文件上下文"
```

### 场景 4：多用户隔离

```bash
# 用户 A 发文件
curl -X POST :9527/local/inbox/file \
  -d '{"user_id":"local:a", "file_path":"/path/to/合同.pdf"}'

# 用户 B 发文字
curl -X POST :9527/local/inbox/text \
  -d '{"user_id":"local:b", "text":"你好"}'

# 查看用户 A 的状态（应该看到 pending_files）
curl -s ":9527/local/state?user_id=local:a" | python3 -m json.tool

# 查看用户 B 的状态（应该没有 pending_files）
curl -s ":9527/local/state?user_id=local:b" | python3 -m json.tool
```

## AI 编排自动化测试的推荐模式

如果你让 AI（如 Claude Code）来编排测试，推荐这个模式：

```
1. POST /local/inbox/text { text }            → 发消息，得到 message_id
2. GET /local/outbox?since=N&wait_ms=15000    → 长轮询等回复
3. assert events 中出现期望文本                  → 断言
4. POST /local/reset { user_id }              → 清理
5. 重复 1-4，每次用不同的 since 游标
```

关键技巧：
- **长轮询而非固定 sleep**：用 `wait_ms` 让服务端在你等待时阻塞，事件到达立即返回，比 `sleep(5)` 快得多
- **since 游标增量**：用上一次返回的 `next_seq` 作为下一次的 `since`，不漏事件、不重复
- **reset 隔离用例**：每个测试用例结束后 reset，保证用例间状态独立

## 环境变量

| 变量 | 说明 | 默认值 |
|------|------|--------|
| `LOCAL_TEST_PORT` | 本地 HTTP 服务端口（设置后激活测试模式） | 无（不激活） |

仅此一个变量。不设它，bot 就完全是原来的微信 bot。

## 故障排查

| 症状 | 可能原因 | 解决方法 |
|------|---------|----------|
| `Connection refused` | bot 没启动 | `pm2 start` 或手动 `node bot.js` |
| `Connection refused` | 端口不对 | 检查 `LOCAL_TEST_PORT` 环境变量 |
| outbox 返回空数组 | 等待时间不够 | 增大 `wait_ms`（AI 调用可能需 10-30s） |
| AI 回复超时或报错 | API key 无效或网络不通 | 检查 `instances/test-local/config.json` |
| 文件解析失败 | document-service 没启动 | `curl :8770/health` 检查 |
| state 返回 `null` | user_id 拼写错误 | 确认 user_id 以 `local:` 开头 |

## 安全注意事项

- HTTP 服务**只监听 127.0.0.1**，外部网络无法访问
- **绝对不要**在生产实例的环境变量中设置 `LOCAL_TEST_PORT`
- 测试实例的 `config.json` 含 API key，已通过 `.gitignore` 保护
- 每次测试调用都会消耗 AI API 额度，建议测试实例指向便宜模型
