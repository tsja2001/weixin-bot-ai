## 验证结果

### 1. 单元验证

- 启动 `LOCAL_TEST_PORT=19527 node bot.js`（在 instances/test-local/）
- `GET /local/health` → 200 `{"ok":true}`
- `POST /local/inbox/text` → 200 `{"ok":true, "message_id":"..."}`
- `GET /local/outbox?since=0&wait_ms=15000` → 包含 AI 回复

### 2. 文件流程验证

- `POST /local/inbox/file` 传入 `test.txt` → `_local_path` 短路读取成功
- outbox 依次收到："已收到...正在解析" → "已收到...约 43 字内容...请告诉我您的要求"
- `GET /local/state` → `pending_files.count=1`, 文件名为 `test.txt`
- 跟进文字 `POST /local/inbox/text` → pending_files 清空

### 3. 生产零侵入验证

- 不设 `LOCAL_TEST_PORT` 启动 bot → 照常进入扫码/session 流程
- 无任何 `[LOCAL]` 日志输出
- `isLocalEnabled()` 返回 `false`，`isLocalId()` 返回 `false`

### 4. 协议一致性

- 对照 `instances/tsja/logs/debug_messages.jsonl` 中的真实 iLink 消息
- 构造器输出字段一一对应（message_id, from_user_id, context_token, message_type, message_state, item_list 及其内部结构）
- 仅 `_local_path` 为内部扩展字段，真实 iLink 永不出现

### 5. 参数校验

- 非法 `user_id`（不以 `local:` 开头）→ 400 错误
- 缺失 `text` 字段 → 400 错误
- 文件不存在 → 400 错误，含清晰的错误消息

## 后续建议

1. **性能**：当前版本已满足自动化测试需求；如需更高的测试吞吐量，可考虑在 inbox 和 outbox 增加批量接口
2. **mock_ai 开关**：可在 `config.json` 增加 `mock_ai` 字段，当为 true 时跳过真实 AI 调用返回固定文本，降低测试 token 消耗（计划书风险表中提及，本期未做）
3. **CI 集成**：可将测试脚本加入 CI 流程，确保每次改动后自动化验证核心路径
